# Отчёт по лабораторной работе: GitHub Actions

## Контрольные вопросы

### 1. Из каких элементов состоит workflow и как они вложены друг в друга?

Workflow это один YAML-файл в каталоге `.github/workflows/`. В нём указывается имя (`name`), событие запуска (`on`) и набор заданий (`jobs`). Каждое задание (job) содержит `runs-on` (на какой машине запускать) и список шагов `steps`. Шаг это либо shell-команда (`run`), либо готовый action (`uses`). Вложенность: workflow → jobs → job → steps → step.

### 2. Чем job отличается от step?

Job это набор шагов, который выполняется на одной отдельной виртуальной машине (runner). Jobs по умолчанию идут параллельно, и у каждого чистая машина. Step это одна команда или один action внутри job; шаги одного job идут по очереди на одной машине и видят файлы друг друга.

### 3. Чем запуск по push отличается от запуска кнопкой (workflow_dispatch)?

Запуск по `push` происходит автоматически при каждой отправке коммита в репозиторий. Запуск через `workflow_dispatch` происходит вручную: человек нажимает кнопку **Run workflow** во вкладке Actions, коммит для этого не нужен. Кнопка появляется, только если файл с таким триггером уже лежит в основной ветке.

### 4. Как безопасно передать в workflow пароль или токен?

Нужно сохранить его в секретах репозитория (Settings → Secrets and variables → Actions) и использовать в workflow как `${{ secrets.ИМЯ }}`. В логе GitHub заменяет значение секрета звёздочками `***`. Нельзя писать пароли и токены прямо в YAML-файл или в код репозитория, потому что они станут видны всем, у кого есть доступ к коду.

### 5. Что такое артефакт и зачем он нужен?

Артефакт это файл (или набор файлов), который job сохраняет после выполнения через `actions/upload-artifact`. Он нужен, чтобы передавать результаты между jobs (у каждого job отдельная машина, и файлы с одной не видны на другой), а также чтобы скачать результат сборки со страницы запуска.

### 6. Как заставить один job дождаться завершения другого? Зачем нужен линтер, если есть тесты?

Для ожидания в job указывают `needs: имя_другого_job`: он стартует только после успешного завершения того job. Линтер нужен, потому что проверяет код без запуска и находит ошибки стиля и потенциальные проблемы, которые тест не заметит, если они не влияют на проверяемый результат. В задании 3 так и было: после удаления кавычек в `hello.sh` тест остался зелёным (вывод не изменился), а линтер shellcheck стал красным и предупредил, что переменная `$1` без кавычек может привести к лишнему разбиению слов (SC2086).

## Вопрос из задания 4

### Что произошло с job `show` после удаления `needs: build` и почему?

ЗАПОЛНИТЕ по тому, что вы увидели в запуске. Без `needs: build` оба job стартуют одновременно. Job `show` запускается на своей чистой машине и пытается скачать артефакт `report`, но `build` ещё не успел его создать и загрузить, поэтому шаг скачивания может завершиться ошибкой (артефакт не найден). Строка `needs` задаёт порядок: `show` ждёт, пока `build` закончится и загрузит файл.
